## 2. WHAT WAS BUILT

### Environment (new this session)

There was no venv and no `requirements.txt`; `sklearn` was not installed.
Created `.venv/` at the project root and froze `requirements.txt`.

    python3 -m venv .venv
    .venv/bin/pip install pandas scikit-learn catboost shap matplotlib

ALWAYS run pipeline scripts with `.venv/bin/python`, not bare `python3` —
the system interpreter has none of these packages.

`.gitignore` gained `models/` and `catboost_info/` (CatBoost writes a training
log directory into CWD on every fit). Note: `.gitignore` has a stray trailing
`EOF` line that predates this session — harmless, left alone, not mine to fix
silently.

### step3_split.py

- Reads the cohort from `step2_features.csv`. Does NOT reconstruct or re-filter.
- Two-stage `train_test_split`: carve off test, then split the remainder.
  70/15/15, stratified on the 4-class label, `random_state=42`.
- Writes `train_rids.csv` / `val_rids.csv` / `test_rids.csv` (single RID column).
- Result: **train 569 / val 122 / test 123**, zero pairwise RID overlap
  (asserted, not just printed).

### step4_processing.py

- Median imputation (numeric) + mode imputation (categorical), fit on TRAIN ONLY.
- Missingness indicators for features >10% NaN in train. **Zero were created** —
  worst feature is EcogSPOrgan at 5.5%. This is correct, not a bug; do not
  "fix" it by lowering the threshold to force indicators into existence.
- `CogIndex = (normalized MMSE) - (normalized CDRSB) - (normalized ADAS13)`,
  computed from the already-normalized components.
- Z-score normalization fit on train only. RID, label, and PTGENDER are excluded
  from normalization (34 of 36 columns get normalized).
- Output: `step4_{train,val,test}.csv` (38 cols each) + `step4_manifest.json`
  recording every imputation median/mode, every normalization mean/std, the
  indicator list, and the CogIndex formula.

ORDER MATTERS AND IS EASY TO MISREAD: imputation runs BEFORE normalization, so
the manifest's mean/std are the post-imputation train statistics. Comparing them
against raw (pre-impute) train stats produces a spurious mismatch on any feature
with NaNs. This tripped the mid-session audit before being traced correctly.

### step5_catboost_shap.py

- CatBoost `MultiClass`, PTGENDER via `cat_features` (never one-hot).
- Val split used as `eval_set` with `early_stopping_rounds=50` and
  `use_best_model=True`.
- Hyperparameter sweep over depth {4,5,6} x l2_leaf_reg {3,5,10} x
  learning_rate {0.03,0.1} = 18 configs. **Selected on VAL accuracy only**;
  test is not consulted until the winner is fixed. Ties break toward the more
  regularized model (shallower first, then stronger L2).
- SHAP `TreeExplainer` on the test set, Top-K by mean |SHAP| (default K=20).
- Outputs to `models/`: `step5_catboost.cbm`, `step5_topk_features.json`,
  `step5_shap_values.npz`, `step5_shap_bar.png`, `step5_metrics.json`
  (the metrics JSON records all 18 sweep results, not just the winner).

`run()` accepts a `grid=` argument. This is the hook the master runner uses to
pin hyperparameters — do not remove it.

### preprocessing.py (master runner, project root)

- Steps 0-4 run as **subprocesses** (they are pure CLI scripts; step0 has no
  `run()` function at all, only `main()`). Step 5 is **imported** so its `grid=`
  can be controlled. This split is deliberate, not an inconsistency.
- `--from-step N` resumes without rerunning earlier steps.
- `--skip-sweep` pins the selected params instead of re-running the grid.
- Fail-fast: every step's output is validated against known-good shapes before
  the next step runs. On mismatch it prints which step failed and why, stops,
  and exits 1.

Runtimes: full pipeline **17.1s**, `--from-step 3` 13.6s, `--from-step 3
--skip-sweep` **3.5s**. step0 rebuilds from 752M of raw in ~4s, so `--from-step`
matters far less than expected — the sweep was the only real cost.

## 3. THE OVERFITTING FINDING (real, partially fixed)

The first step5 run scored **train 0.9912 / val 0.8115 / test 0.7967** — a
19.5-point train-test gap. This was flagged rather than accepted.

Investigation first ruled out the obvious suspect: early stopping was NOT being
ignored. The original model stopped at 160 trees of a 1000 cap, so
`use_best_model=True` was working. The overfit came from capacity (depth 6,
l2_leaf_reg 3), so the sweep grid was biased toward shallower trees and
stronger L2.

    metric      before    after     delta
    train       0.9912    0.9701    -0.0211
    val         0.8115    0.8361    +0.0246
    test        0.7967    0.8130    +0.0163
    train-test  0.1945    0.1571    -0.0374

Selected params: **depth=6, l2_leaf_reg=10, learning_rate=0.1**, 265 trees.

### Three honest caveats — do not let these get lost

1. **A 15.7-point gap remains.** Regularization bought ~3.7 points of it. This
   is not solved, only improved.

2. **The selection is weakly grounded.** Val is 122 subjects, so one subject is
   0.82 points. The top 13 of 18 configs span 0.8033-0.8361 — a spread of four
   subjects. The winner *tied exactly* with depth=6/l2=3/lr=0.1 and was chosen
   by the regularization tiebreak, not by a real margin. Treat the selected
   config as one of a dozen statistically indistinguishable options.

3. **The gap-minimizing config was deliberately NOT chosen.**
   depth=4/l2=10/lr=0.03 has the smallest gap (train 0.8963 / val 0.8197, gap
   7.7 points) but lower val accuracy. Picking it would improve the gap number
   while predicting worse. It is recorded under `sweep` in `step5_metrics.json`
   if anyone wants it.

If a genuine reduction is wanted, the lever is **cross-validation** (e.g. 5-fold
CV over train+val for both selection and estimation), not more grid points.
More tuning against a 122-subject val set is fitting noise. That is a step3
split-strategy change, so it was left alone.

## 6. KNOWN GAPS (none are defects, all are worth knowing)

- **`step5_shap_values.npz` does not store the base/expected value**, only the
  per-feature contributions. Additivity therefore cannot be checked from that
  artifact alone. Worse, `shap.TreeExplainer(model).expected_value` returns
  **nan** for multiclass CatBoost — to recover the base, use
  `model.get_feature_importance(pool, type="ShapValues")`, whose last column is
  the bias. Additivity was verified this way and holds exactly (base is constant
  across all 123 subjects, std = 0.0; shap-lib values vs CatBoost native differ
  by 0.000e+00).

- **`preprocessing.py` hardcodes the expected shapes** (`EXPECTED`,
  `EXPECTED_SPLIT_ROWS`, `STEP4_COLS`). That is what makes fail-fast meaningful,
  but a *legitimate* cohort change — an ADNI data refresh, a step2 threshold
  change — will trip the guard and require updating those constants. Intended
  behaviour, but it will look like a failure the first time it happens.

- **The 122-subject val set is small enough that hyperparameter selection is
  near-noise.** See section 3, caveat 2.

## 8. WHAT IS NEXT

The clinical pipeline as specified in `docs/context.txt` is **complete**. All
seven deliverables (step0-step5 plus `preprocessing.py`) exist, run end-to-end
from raw data, and are verified.

What remains is the **fusion interface** — the reason this pipeline exists.
Per `docs/context.txt`, the clinical stream's Top-K feature vector gets
concatenated with `[DEMO, ALZ]` from the teammate's MRI stream and fed to a KAN
with two heads (`COG` 4-class softmax, `ADD` binary sigmoid).

Nothing has been built for that yet. Open questions to settle with the teammate
before building it:

- What RID set does the MRI stream cover, and how does it intersect our 814?
  Our split must be reused (train/val/test RID lists are on disk for exactly
  this reason) or the fusion model will leak across splits.
- Does the KAN consume the Top-K columns only, or all 36? `step5_topk_features.json`
  has the Top-K list; the filtered matrices are derivable from the step4 CSVs.
- `[DEMO, ALZ]` need z-score alignment with our features. Our normalization
  stats are train-fit and live in `step4_manifest.json` — the MRI side must fit
  its own stats on the SAME train RIDs, not on its own split.

### Optional improvements, in priority order

1. **Cross-validation for step5 selection** (see section 3). The single highest-
   value change if model quality matters more than pipeline completeness.
2. Save the SHAP base value into the npz (section 6).
3. Consider whether the LMCI weakness warrants class weighting — but note that
   accuracy is currently the only selection metric, and macro-F1 might be the
   more honest target given the class imbalance (EMCI 310 vs AD 151).

## 9. STANDING GOTCHAS (session 3 additions)

Everything in context2.txt section 9 still applies. New:

- Run scripts with `.venv/bin/python`. The system Python has no dependencies.
- step4 imputes BEFORE normalizing. Manifest mean/std are post-imputation
  statistics. Comparing them to raw train stats gives a false mismatch.
- step5's zero missingness indicators are correct (max NaN 5.5% < 10%).
- Never select hyperparameters on test. The sweep uses val only, by design.
- Do not one-hot PTGENDER anywhere. It is the registered CatBoost categorical
  and step4 deliberately leaves it unnormalized.
- CatBoost writes `catboost_info/` into the working directory on every fit.
  It is gitignored; delete it freely.
- The 4-class labels are final and verified twice over (session 2 by audit,
  session 3 by full 814-subject re-derivation from raw). Do not collapse
  EMCI/LMCI.
